# Vivaldi UI-mod loading research — 8.3.4191.26

**Scope:** Primary-source reference review for the inspected build. These references explain loading and signing constraints; they do not prove runtime behavior or permanent-install launch compatibility. See [the investigation](investigation.md) for the separate local runtime checks.

## Findings

- **Prefer `window.html` as the documented JS hook, not `main.html`.** Vivaldi’s pinned [forum modding guide](https://forum.vivaldi.net/topic/10549/modding-vivaldi) directs users to add `<script src="custom.js"></script>` inside `window.html`’s `<body>`, then restart. It documents CSS mods separately through `chrome://flags/#vivaldi-css-mods` and Appearance → Custom UI Modifications. It also warns JS edits are wiped by updates. Given the reported `main.html` bundle bootstrap and minimal `window.html`, a one-line loader in `window.html` is the lower-coupling documented hook—but still an unsupported mod, not a public compatibility guarantee.
- **macOS signing impact is real.** The reported file sits inside `Vivaldi Framework.framework` in the app bundle. Apple’s [TN2206](https://developer.apple.com/library/archive/technotes/tn2206/_index.html) says the v2 resource envelope records substantially all bundle files and verifies nested code. Editing `window.html` therefore invalidates the existing signature; `codesign` verification can fail. Whether Gatekeeper blocks or warns at launch depends on system policy and app provenance. Keep the installed app untouched; test only a disposable app copy. Do not rely on re-signing to restore Vivaldi’s vendor identity.
- **Test without personal data:** launch that copy, when ready, with a fresh `--user-data-dir=/tmp/vivaldi-mod-test` (Chromium documents this override [here](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/user_data_dir.md)); verify the active path in `vivaldi://version` and do not sign into Sync. Keep the pristine HTML and mod source outside the app so the patch can be reverted.
- **API and multiwindow limits:** Chrome documents [`tabs`](https://developer.chrome.com/docs/extensions/reference/api/tabs), [`windows`](https://developer.chrome.com/docs/extensions/reference/api/windows), and [`tabGroups`](https://developer.chrome.com/docs/extensions/reference/api/tabGroups) as extension APIs. Tab groups expose flat fields (title, color, collapsed, window ID), not parent/child nesting. These docs do **not** guarantee those bindings—or Vivaldi-private APIs—in this build’s `window.html` context. The forum guide also does not specify per-window execution cardinality. Treat API availability and one-instance-per-window behavior as REA/runtime checks; make initialization idempotent and keep shared folder state outside a single window global.
